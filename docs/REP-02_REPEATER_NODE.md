# Echolet: Docker Repeater Specification (REP-02)

## 1. Назначение репитера
Репитер (`Relay Node`) — это серверный узел, работающий 24/7. В MVP его задача не в предоставлении полной анонимности, а в обеспечении доступности сети и offline-доставки.

Основные роли репитера:

* принимать и хранить зашифрованные offline-пакеты;
* публиковать собственную доступность и транспортные параметры;
* хранить `PreKey Bundle` устройств;
* помогать клиентам доставлять сообщения, когда адресат оффлайн;
* в более поздних фазах — участвовать в relay и onion-маршрутизации.

---

## 2. Технический стек
* **Core:** `Go`.
* **Transport MVP:** HTTP JSON API over TLS (HTTPS, возможна TLS-терминация reverse proxy); локальный HTTP — только для разработки. `go-libp2p`/QUIC — будущие adapters, см. [STACK-14](STACK-14_TECH_DECISIONS.md).
* **Storage:** `BadgerDB` для mailbox, prekey records и временных индексов.
* **Container:** `Docker`.
* **Runtime Goal:** минимальный образ, подходящий для домашних серверов и VPS.

---

## 3. Границы ответственности в MVP

### 3.1. Что репитер делает
* Хранит зашифрованные mailbox-объекты.
* Отдает `PreKey Bundle` по запросу.
* Выполняет challenge-response для подтверждения владения mailbox.
* Ограничивает злоупотребления через rate limiting, quotas и TTL.
* Предоставляет минимальную диагностику владельцу узла.

### 3.2. Что репитер не делает
* Не расшифровывает пользовательские сообщения.
* Не считается доверенной стороной для identity.
* Не разрешает callsign в IP как источник истины.
* Не гарантирует анонимность отправителя или получателя.
* Не хранит долгосрочные логи трафика содержимого.

---

## 4. Основные модули

### 4.1. Mailbox Storage
Если целевой клиент недоступен, репитер принимает `sealed_payload` и сохраняет его в mailbox получателя.

Минимальная запись:

* `mailbox_id`;
* `message_id`;
* `sealed_payload`;
* `payload_type` (`message`, `receipt`, `prekey_refill`, `invite`, ...);
* `created_at`;
* `expires_at`;
* `size_bytes`.

Требования:

* payload не должен быть читаем репитером;
* mailbox читается только после challenge-response;
* выдача выполняется пакетно с подтверждением доставки или истечения TTL.

### 4.2. Mailbox Authentication
Механизм доступа к mailbox должен быть криптографически проверяемым.

Базовый flow:

1. Клиент подписывает запрос создания challenge ключом устройства.
2. Репитер проверяет опубликованное устройство, связь его identity с mailbox и подпись; возвращает `challenge_id`, `nonce`, `expires_at_ms`.
3. Клиент подписывает poll с точным nonce из ответа ключом того же устройства.
4. Репитер сверяет mailbox/device challenge, срок/used, ownership и подпись; инвалидирует challenge перед выдачей очереди.
5. Клиент отдельно подписывает ack со списком envelope IDs; relay снова проверяет ownership и подпись.

Точные UTF-8 строки подписи и ограничения replay: [PROTOCOL-07 §9.6–9.8](PROTOCOL-07_MVP_MESSAGE_FLOW.md#96-post-v1mailboxchallenge). Производный mailbox-ключ в текущем API не используется.

Это снижает риск неавторизованного перебора mailbox-идентификаторов.

### 4.3. PreKey Bundle Registry
Репитер может выступать как хранилище опубликованных prekey-наборов:

* принимает только подписанные bundle;
* хранит активную версию и ограниченное число резервных записей;
* отдает bundle без права модификации содержимого;
* может сигнализировать устройству о необходимости пополнить `one_time_prekeys`.

### 4.4. Relay Transport
В MVP репитер поддерживает базовый relay path для зашифрованных пакетов между клиентом и mailbox-слоем. Полноценный multi-hop onion relay выносится в отдельную фазу.

### 4.5. Discovery Records
Репитер публикует только собственные signed records:

* `relay_id`;
* `relay_pubkey`;
* поддерживаемые транспорты;
* адреса для подключения;
* TTL записи.

Репитер не должен публиковать список клиентских контактов в открытом виде.

## 5. Модель данных

### 5.1. Основные bucket'ы хранения
* `mailboxes/` — очередь зашифрованных объектов по `mailbox_id`.
* `prekeys/` — опубликованные `PreKey Bundle`.
* `relay-record/` — собственная подписанная запись узла.
* `abuse-counters/` — rate limits, quotas, penalties.

### 5.2. TTL и очистка
* текстовые сообщения: до 7 дней;
* служебные пакеты: 24-72 часа;
* истекшие prekey-записи: удаляются после истечения валидности;
* очистка выполняется фоновым job-процессом.

## 6. Конфигурация
Параметры ниже описывают целевой операторский интерфейс; фактические env-переменные проверяются по `apps/relay/internal/config`. QUIC endpoint не требуется для MVP.
Репитер настраивается через `docker-compose.yml` или переменные окружения.

| Переменная | Описание | Пример |
| :--- | :--- | :--- |
| `NODE_CALLSIGN` | Человекочитаемое имя узла | `RPT-AD-01-RYZEN` |
| `MAX_STORAGE_BYTES` | Общий лимит mailbox-хранилища | `21474836480` |
| `MAILBOX_TTL_HOURS` | TTL сообщений по умолчанию | `168` |
| `MAX_MESSAGE_BYTES` | Максимальный размер одного объекта | `262144` |
| `ECHOLET_HTTP_ADDR` | Реальный внутренний HTTP listener за TLS reverse proxy | `:8081` |
| `DASHBOARD_PORT` | Порт локального dashboard | `8080` |
| `ALLOW_RELAY_TRANSPORT` | Разрешить relay path | `true` |

В MVP конфигурация не включает обязательные anti-DPI параметры. Они могут быть добавлены позже как transport extensions.

## 7. Dashboard (Local Monitor)
Локальный UI должен быть полезен владельцу узла, но не разрушать privacy-модель.

Разрешенные панели:

* **Node Health:** uptime, версия, загрузка CPU/RAM, состояние диска.
* **Traffic Stats:** количество принятых/выданных mailbox-объектов, объем за период.
* **Storage Usage:** использование quota и истекающие TTL.
* **Transport Status:** доступность HTTP API и внешнего HTTPS endpoint.

Не должны отображаться:

* plaintext сообщений;
* долгосрочная история IP клиентов;
* открытый список пользовательских контактов;
* deanonymizing correlation data, если это не требуется для краткоживущей отладки локально.

---

## 8. Безопасность узла
* **Self-Healing:** автоматический restart процесса и health checks контейнера.
* **Rate Limiting:** ограничения по записи, чтению и публикации prekeys.
* **Quota Enforcement:** лимиты на mailbox и на общий storage.
* **Zero-Log Policy:** по умолчанию не хранить IP-адреса и содержимое payload в постоянных логах.
* **Key Isolation:** приватный ключ репитера хранится отдельно и не должен попадать в dashboard/UI.
* **Abuse Controls:** защита от mailbox flooding, oversized payloads и replay попыток.

---

## 9. Что выносится в следующие фазы
Следующие возможности не требуются для первой версии репитера:

* 3-hop onion routing engine;
* глобальный gossip-обмен клиентскими callsign;
* transparent media relay для больших файлов;
* stealth-wrapper уровня anti-DPI;
* публичная карта всех пиров сети.
