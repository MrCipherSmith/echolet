# Echolet: Signal bundle v2

Дата: 2026-09-06. Область: версионированный JSON-контракт и Node adapter для официального libsignal. Relay endpoints и мобильный bridge этим документом не объявляются реализованными.

## Зачем нужна отдельная версия

Bundle v1 не содержит ключи Kyber и использует другую модель session keys. Новый тип `signal_prekey_bundle`, `version: 2`, `suite: libsignal-pq-v1` не заменяет и не переинтерпретирует v1. Существующие v1 routes и validators сохраняются.

## Цепочка доверия

1. Получатель заранее знает ожидаемые Echolet identity и device ID из доверенного контакта.
2. Root Ed25519 identity подписывает DeviceRecord v1. Из проверенной записи берётся device Ed25519 public key.
3. Device key подписывает весь v2 bundle: Signal identity, registration ID, EC/Kyber prekeys, вложенные подписи, срок действия и DeviceRecord.
4. Официальный libsignal проверяет внутренние EC/Kyber signatures. Получатель явно закрепляет Signal identity и создаёт сессию; импорт JSON сам по себе доверие не меняет.

Signal identity не равна Echolet root/device signing key. Native address выводится локально из проверенных identity и полного UUID устройства: JSON-массив этих двух строк становится name, native deviceId всегда 1. Ответ relay не задаёт произвольный native address.

## Формат и подпись

Объекты строгие: неизвестные поля, некорректный base64url, неправильная длина/префикс ключа, несовместимая версия или suite отклоняются. Числовые поля — целые в заданном диапазоне. Bundle имеет срок не более семи дней; импорт отвергает ещё не действующие и истёкшие записи.

V2 подписывает фиксированный JSON tuple с domain separator `echolet.signal.prekey_bundle.v2`. В него входят все вложенные подписи; исключается только внешняя signature. Это избегает расхождений старых JS/Go canonicalization helpers. Полная форма tuple и диапазоны полей заданы в [спецификации реализации](../.metaproject/flows/001-2026-09-05-echolet-assessment-fixes/signal-wire-v2-spec.md).

Legacy-подпись DeviceRecord проверяется на исходном строгом объекте с сохранением порядка вложенных capabilities. Успешная проверка JS не доказывает совместимость старого Go verifier: перед relay-интеграцией обязательны общие fixtures.

## Одноразовые ключи и доставка

`one_time_prekey` равен null либо содержит один EC prekey. В этой версии реализации он предназначен для прямого обмена bundle между клиентами. Повторная публикация объекта не превращает ключ в одноразово выдаваемый: для relay необходимы транзакционное выделение, сохранение истории потребления и правила повторных запросов.

Нельзя удалить ключ из подписанного batch и вернуть изменённый объект со старой подписью. Нельзя сбросить историю потребления повторной публикацией. Пока эти правила не реализованы и не проверены, v2 не подключается к существующему v1 fetch.

## Проверка и оставшаяся работа

Критерии: JSON roundtrip двух независимых native sessions, ответы, подмена каждого звена доверия, некорректные signatures/TTL/encoding, неизменность pinned trust, совместимость прежних тестов. Итоговые результаты фиксируются в [текущем статусе](STATUS_CURRENT.md).

Следом нужны relay v2 с общими JS/Go fixtures и атомарной выдачей prekeys, mobile bridge, защищённое хранение ключей, контакты и проверки устройств. Этот формат не является подтверждением готовности защищённого MVP.
