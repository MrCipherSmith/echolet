# Echolet: Frontend & Mobile Client Specification (APP-03)

## Статус реализации и ограничение демонстрации

Этот документ описывает целевой клиент. Актуальная готовность — в [STATUS_CURRENT.md](STATUS_CURRENT.md). Текущий session engine не принят как production E2EE. Экран messaging по умолчанию отключён; доступен только в development-сборке с явным `EXPO_PUBLIC_ECHOLET_ENABLE_UNSAFE_DEMO=true` и постоянной пометкой демонстрации. В release-сборке этот флаг не включает переписку. Ограничение не исправляет сам протокол и сохраняется до прохождения session/contact/security gates.

## 1. Назначение клиента
Мобильный клиент Echolet — это secure messenger с P2P- и relay-архитектурой, ориентированный на:

* создание автономной личности;
* защищенный обмен текстовыми сообщениями;
* работу через доверенный репитер (`Home Base`);
* инженерно прозрачный интерфейс без перегрузки пользователя низкоуровневыми деталями.

В первой версии приоритет отдается надежности и реализуемости на iOS/Android, а не максимально широкому набору transport-функций.

## 2. Технологический стек

### 2.1. Базовый стек MVP
* **Framework:** `React Native`.
* **App Runtime:** `Expo` допустим только на этапе прототипа; production-архитектура должна допускать переход на bare/native workflow.
* **State Management:** `Zustand` для локального UI-state.
* **Async Data:** `React Query` для сетевых операций, фоновой синхронизации и повторных запросов.
* **Local DB:** `SQLite` с шифрованием на уровне устройства или совместимой encrypted storage abstraction.
* **Key Storage:** OS keystore / Keychain для seed, device keys и session secrets.
* **Styling:** `NativeWind` или иной слой, не мешающий производительности и системной интеграции.

### 2.2. Технологические ограничения
Следующие решения не считаются гарантированными для MVP и требуют отдельной валидации:

* `js-libp2p` в production mobile runtime;
* `Wi-Fi Aware` как кроссплатформенная фича;
* глубокая background P2P-активность на iOS;
* fully managed Expo при использовании нативной криптографии, SQLCipher и постоянных сетевых transport'ов.

## 3. Архитектура интерфейса
Гибридная модель UX: современный мессенджер с читаемой инженерной телеметрией.

### 3.1. Основные экраны
1. **Журнал (Logbook):** список диалогов, статусы доставки, unread-счетчики.
2. **Чат (Conversation):** основной экран переписки, текстовые сообщения и системные события.
3. **Терминал (Console):** диагностический экран с понятной телеметрией: handshake, relay delivery, prekey fetch, latency.
4. **Контакты (Contacts):** добавление контакта через QR, invite packet или fingerprint.
5. **Настройки (Settings):** управление seed-фразой, устройствами, доверенным репитером, локальной безопасностью.

### 3.2. Визуальный язык
* **Тема:** темный интерфейс в радио-эстетике.
* **Акценты:** `#00FF41` для подтвержденных сетевых состояний, `#FFB000` для предупреждений, приглушенные серые для фона.
* **Типографика:** моноширинный шрифт для телеметрии и нейтральный sans-serif для основного текста.
* **Статусы:** вместо обычных галочек используются уровни канала: `queued`, `relayed`, `delivered`, `verified`.

## 4. Основные функции MVP

### 4.1. Onboarding и личность
* Генерация seed-фразы.
* Подтверждение пользователем сохранения seed.
* Генерация `Identity Key`.
* Создание `Device Key` и первичного `Signed Device Record`.
* Генерация callsign как UX-aliаs.

### 4.2. Contact Exchange
Поддерживаемые способы первого контакта:

* **QR-код рядом:** основной и самый надежный способ для MVP.
* **Invite Packet:** зашифрованное или подписанное приглашение через репитер.
* **Fingerprint Entry:** ручной ввод короткого safety number для подтверждения контакта.

Удаленный поиск по глобальному callsign-каталогу не обязателен для первой версии.

### 4.3. Secure Messaging
* Получение `PreKey Bundle` контакта.
* Установление сессии по `X3DH`.
* Дальнейший обмен через `Double Ratchet`.
* Отправка сообщений через `Home Base`, если peer недоступен напрямую.
* Получение и подтверждение сообщений из mailbox.

### 4.4. Local Security
* Биометрическая защита приложения.
* Локальное шифрование базы.
* Ручная очистка истории.
* Настраиваемый `Auto-Purge` для локальных копий сообщений.

## 5. Функции следующих фаз

### 5.1. Локальный discovery поблизости
BLE и другие proximity-механики полезны, но не обязательны для MVP. Они выносятся в следующую фазу после стабилизации базового messaging stack.

### 5.2. Onion / Multi-hop Telemetry
Терминал может показывать hop'ы только тогда, когда multi-hop routing реально реализован. До этого он отображает фактические события: `home-base relay`, `bundle fetched`, `mailbox polled`, `session rotated`.

### 5.3. Media Transfer
Передача больших медиафайлов выносится в отдельную фазу. Для MVP допустимо ограничиться текстом и компактными системными вложениями.

## 6. Локальная модель данных
Клиент хранит у себя:

* seed и ключи — только в защищенном системном хранилище;
* profile и callsign;
* список контактов с fingerprint и trust status;
* device records контактов;
* active sessions;
* локальную копию сообщений;
* TTL и purge-политику.

Важно:

* публичные ключи контактов не считаются секретом;
* защищать нужно их целостность, связку с identity и локальное состояние сессий;
* plaintext сообщений в базе должен быть минимально необходимым и контролироваться политикой retention.

---

## 7. Фоновая логика

### 7.1. MVP
В первой версии клиент выполняет:

* периодический mailbox poll;
* доставку исходящих сообщений через `Home Base`;
* обновление prekeys и device records;
* ограниченную синхронизацию при возврате приложения в foreground.

### 7.2. Ограничения мобильных ОС
Клиент должен учитывать, что iOS/Android ограничивают:

* длительные фоновые сетевые соединения;
* локальный P2P discovery в фоне;
* надежное поддержание transport-сессий без push-механики.

Поэтому push/wake-up инфраструктура рассматривается отдельно и не должна искажать обещания MVP.

---

## 8. Звуковой и атмосферный слой
Аудио остается вторичным и не должен мешать надежности или доступности:

* мягкий `squelch` при запуске приложения;
* очень деликатный `morse feedback` для системных событий;
* полное отключение всех звуков пользователем.

---

## 9. Что входит в MVP
* identity onboarding;
* callsign generation;
* QR-based contact exchange;
* secure text messaging через `Home Base`;
* mailbox poll и delivery receipts;
* local encrypted storage;
* terminal screen с реальной диагностикой.

В MVP не входят:

* обязательный BLE/Wi-Fi Aware discovery;
* гарантированная background P2P-связность;
* production-ready multi-hop onion UI;
* крупные media transfer flows.
