## Открытые ограничения

1. **Затопление mailbox ограничено, но не устранено.** Измерено на реальном relay-бинарнике при конфигурации по умолчанию: 48 конвертов максимального размера ещё доставляют легитимное сообщение, **49 — заклинивают mailbox**. Для этого теперь нужны **4 самостоятельно опубликованные личности** (было 1) плюс 49 POST-запросов, около **12,85 МБ**, менее чем за 30 секунд и в пределах штатного лимита 120 запросов/мин. Заклинивание держится **до 168 ч** — предела хранения. В режиме, ограниченном количеством, цена — 50 личностей и 800 конвертов. Корневая причина открыта: `POST /v1/device-records/publish` сам по себе не аутентифицирован, поэтому личность стоит один бесплатный запрос. Три раунда исправлений (курсор и ограниченный обход страниц, аутентификация отправителя, квота на отправителя) каждый поднимали цену атаки и каждый признавали класс незакрытым. **Пользователю показали эти измеренные числа, и он решил зафиксировать это как задокументированное ограничение, а не расширять область работ дальше.**
2. **Один опубликованный bundle обслуживает ровно одного первого отправителя.** У `rotateBundle()` и `retryPending()` нет точки входа в CLI — сознательное решение не ломать замороженную поверхность команд, — поэтому после того как первый отправитель востребовал bundle получателя, второй отличный отправитель получает `PREKEY_BUNDLE_UNAVAILABLE`, а повторная публикация сообщает `claimable: false` вместо восстановления доступности. Ни один критерий приёмки при этом не нарушается: ни один из них не требует, чтобы двое разных отправителей дошли до одного получателя.
3. **Бюджет байт на poll не связан с `ECHOLET_MAX_MESSAGE_BYTES`.** При `maxMessageBytes` = 2 MiB relay вернул ответ на 2 097 781 байт — примерно вдвое больше жёсткого предела клиента, и ничего не было подтверждено. При значении по умолчанию 262144 недостижимо.
4. **Устойчивость backfill.** `BackfillDeviceMailboxBindings` — единственный писатель `device_mailbox` без ограниченного повтора при конфликте, и одна нерасшифрованная запись прерывает весь скан: измерено 0 из 2 здоровых записей связано после одной битой. Стоимость скана при старте ни разу не подтверждена верификатором.
5. **Остатки тестового покрытия.** Курсорный путь `GetEnvelopeBatchFrom`, обслуживающий каждый производственный poll, не имеет теста репозитория с непустым курсором; освобождение бюджета байт для первого конверта переживает удаление; подпись на mobile не наблюдаема ни одним тестом; четыре области исправлений ни разу не были достигнуты мутационным проходом.
6. **Ограничения тестового стенда.** Выше примерно 30-кратной перегрузки CPU vitest теряет результаты целого файла из-за собственного 60-секундного потолка `onTaskUpdate`, и рычага конфигурации для этого нет (при фактической нагрузке гейтов ≤4,8× не наблюдалось ни разу). Строгий health-адаптер не запускает ESLint и не связывает независимо проходящие typecheck и test со своими источниками, поэтому его оценка — совещательная; авторитетным счётом тестов является независимый прогон по workspace.

## Предупреждение о среде выполнения

`apps/cli` объявляет `"engines": {"node": ">=22.13"}`. ## Исправлено в flow 001

- Строгий Signal wire v2 с Kyber и подписью полного bundle ключом устройства; root-signed `DeviceRecord` связывает устройство с ожидаемой identity, native prekey signatures проверяются до импорта, import не меняет trust. [Документ](PROTOCOL-30_SIGNAL_BUNDLE_V2.md).
- Node-only session runtime на официальном libsignal 0.102.0: явное доверие identity, зашифрованное атомарное хранение session/inbox/outbox, точный повтор. Проверены SIGKILL до и после commit, rollback при ошибке COMMIT и восстановление той же очереди.
- CLI-прототип: профили, экспорт и импорт контактных карточек с закреплением Signal identity, публикация bundle, отправка, приём, история и `doctor`; типизированные коды выхода 0/2/3/4/5.
- Relay: конфликт `envelope_id` возвращает 409 вместо перезаписи; истёкшие записи отбрасываются до применения лимитов; каждый v1-декодер ограничен по размеру тела; `size_bytes` сверяется с фактической длиной шифротекста; идентификаторы ограничены по длине; авторизация mailbox опирается на неизменяемую связку `device_mailbox`, а не на обратный поиск по устройству.
- Relay: выдача батча ограничена одновременно количеством и байтами, при этом один конверт максимального размера выдаётся всегда; `next_cursor` стал позицией возобновления, поэтому отвергнутые конверты больше не удерживают окно выборки навсегда; решение о лимите частоты принимается без ввода-вывода под блокировкой, а ключ квоты нормализуется без учёта порта и клиентских заголовков.
- CLI: повторное чтение outbox внутри транзакции мутации; типизированная `PersistenceError`, отличаемая по происхождению, а не по тексту; поконвертное принятие с агрегированным списком `rejected`; ограниченный обход страниц; строгий разбор аргументов сохранён при поддержке значений, начинающихся с дефиса.
- Аутентификация отправителя и квота неподтверждённых конвертов на отправителя (см. решения пользователя выше).
- Messaging на mobile по умолчанию закрыт: требуется `__DEV__ === true` плюс явный `EXPO_PUBLIC_ECHOLET_ENABLE_UNSAFE_DEMO=true`, release не может включить режим через env. Сам криптографический протокол этим не исправлен.
- Повторное использование mailbox challenge конкурентными poll-запросами устранено атомарным consume после проверки подписи и владельца.
- HTTP/TLS и mailbox signing contracts согласованы с кодом; необоснованное сравнительное обещание защиты метаданных удалено.
- Закрыт долг документации по контракту relay/CLI: `claimable`, поле запроса `cursor` и семантика позиции `next_cursor`, форма результата `poll` `{received, more, rejected}`, поле `sender_signature` и его транскрипт, квота на отправителя и коды `PREKEY_BUNDLE_UNAVAILABLE`, `UNAUTHORIZED_MAILBOX_ACCESS`, `SENDER_QUOTA_EXCEEDED` с отображением на коды выхода — [API-11](API-11_JSON_SCHEMAS.md), [PROTOCOL-07](PROTOCOL-07_MVP_MESSAGE_FLOW.md), [спецификация прототипа](requirements/echolet-cli-prototype/specification.md).

## Что не установлено этими проверками

- производственная безопасность и пригодность для чувствительной переписки;
- доставка на мобильных устройствах: `apps/mobile` даёт 6 тестов, проверяющих только состояние блокировки; ни обмена на реальных устройствах, ни рестарта, ни потери связи, ни фоновой доставки не выполнялось (задача flow T10 открыта). Изменение подписи на mobile корректно по построению, но не наблюдаемо ни одним тестом;
- публичное развёртывание и готовность к промышленной эксплуатации;
- завершение независимого криптографического аудита (задача flow T11 открыта);
- пользовательский спрос и пилот: интервью и пилот не проводились (задача flow T12 открыта, [PILOT-29](PILOT-29_VALIDATION_PLAN.md) хранит пустые поля evidence);
- постоянная пригодность зафиксированной зависимости `@signalapp/libsignal-client@0.102.0`, которая взята только для прототипа.

Разрешённое утверждение после прохождения гейта, дословно из [metrics-and-validation.md](requirements/echolet-cli-prototype/metrics-and-validation.md): два локальных компьютерных CLI-клиента обменялись зашифрованным текстом через relay Echolet и восстановились после проверенных перезапусков. К нему прилагается исключение: mailbox **не** защищён от самостоятельно опубликованного отправителя, затапливающего офлайн-получателя.
