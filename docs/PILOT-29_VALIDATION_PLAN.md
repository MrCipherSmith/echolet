# Echolet: Pilot Validation Plan (PILOT-29)

## Статус и назначение

План эксперимента, результаты **pending**. Интервью, device evidence, независимая проверка и пользовательский пилот этим документом не подтверждаются. Числовые пороги ниже — предложенные внутренние критерии решения, не отраслевые нормы и не доказательство спроса.

## Гипотеза ценности

Небольшой круг знакомых хочет текстовую переписку без регистрации по номеру телефона и с сервером под собственным контролем. Один участник готов обслуживать relay; остальные могут подключиться без технического сопровождения. Участники должны назвать конкретную причину выбрать Echolet вместо текущего способа общения. Радио-эстетика сама по себе не считается доказанной потребностью.

## Допуск к пилоту

Все пункты обязательны до набора участников:

1. Gate G0 из [DELIVERY-13](DELIVERY-13_SPRINT_PLAN.md) закрыт: конкретная библиотека и версия, bootstrap/ответы, сохранение сессии после перезапуска, delayed/duplicate сообщения на двух физических телефонах; evidence по [RFC-18](RFC-18_CRYPTO_SELECTION.md).
2. Минимальный путь install → identity → contact → send → offline return → receipt проходит без devtools. M3–M5 принимаются по [TEST-16](TEST-16_ACCEPTANCE_CHECKLIST.md), без подмены ratchet упрощенным шифрованием.
3. Независимый от автора реализации специалист проверил session/keys/storage/auth и модель метаданных. Блокирующие замечания закрыты повторной проверкой. Review не называется полноценным аудитом, если его объем этого не покрывает.
4. Есть матрица iOS/Android: модель, ОС, build, foreground/background/terminated/offline, уведомления и время доставки. Если фон не поддерживается, пилот явно исследует режим «получение после открытия». Если аудитории он не подходит, сначала пересмотреть доставку.
5. Согласованы способ обратной связи, удаление данных, ответственный за relay и процесс остановки пилота. Начинать с несекретной тестовой переписки; отсутствие независимой проверки нельзя компенсировать предупреждением пользователя.

## Проведение

* До разработки следующего большого блока провести 5–8 коротких интервью с потенциальными пользователями: текущий инструмент, конкретные неудобства, цена перехода, кто обслуживает relay, приемлемость открытия приложения ради получения. Записать обезличенные выводы; не выдавать намерение попробовать за удержание.
* После допуска набрать 5–10 существующих пар знакомых. Длительность пилота — 3 недели. Зафиксировать число приглашенных и начавших; выбывшие остаются в знаменателе.
* В первую неделю измерить самостоятельное подключение и первую двустороннюю переписку. Следующие две недели не напоминать писать: фиксировать использование по инициативе участников и причины возврата к другим приложениям.
* Ответственный за пилот ведет минимальную таблицу: код пары, дата начала, результат onboarding, минуты помощи, активные недели, проблема доставки, причина продолжения/отказа. Сообщения, seed, ключи, адреса и контактный граф не собираются. Самоотчеты и обезличенные диагностические результаты хранить локально с согласованным сроком удаления (предлагается 30 дней после решения).
* Владелец relay отдельно учитывает время настройки/поддержки и расходы; после пилота обсуждает готовность продолжать обслуживание либо оплачивать его. Не трактовать ответ как совершенную покупку.

## Предлагаемые критерии решения

| Проверка | Предлагаемый порог | Evidence сейчас |
|---|---|---|
| Самостоятельное подключение | ≥80% начавших пар доходят до двустороннего текста за 10 минут без помощи разработчика | pending |
| Возврат | ≥60% начавших пар общаются по собственной инициативе минимум в 3 разные дня каждой из недель 2 и 3 | pending |
| Причина выбора | ≥60% начавших пар называют конкретную повторяющуюся задачу, для которой предпочли Echolet | pending |
| Управляемость relay | Хотя бы 2 оператора готовы продолжать; каждое вмешательство и расходы записаны | pending |
| Надежность | Нет подтвержденной потери сообщения в пределах TTL, дублирования отображения или ложного delivered в согласованных сценариях | pending |
| Безопасность | Нет открытых блокирующих замечаний независимой проверки | pending |

Данные малой выборки описывают пилот, а не рынок. Проценты публикуются вместе с абсолютными числами; изменение порогов после старта фиксируется как новая версия эксперимента, не как успех прежнего.

## Решение после пилота

* **Continue:** все gates выполнены, критерии достигнуты, есть повторяющаяся потребность и назван ответственный за следующий ограниченный этап. Это допускает следующий эксперимент, а не автоматически всю roadmap.
* **Rework:** спрос наблюдается, но доставка/onboarding не проходят; выбрать один основной дефект, исправить и повторить ограниченный пилот с теми же метриками.
* **Stop / pause:** повторяющаяся потребность не подтверждается, люди не возвращаются или некому обслуживать relay. Сохранить результаты; не добавлять функции ради продления эксперимента.
* При потере данных или security blocker остановить набор и использование до исправления и повторной проверки.

BLE, direct paths, onion/multi-hop, callsign mining, media и public network остаются отложенными до решения. Фактический внешний review, работа на телефонах и интервью требуют реальных участников/устройств и не закрываются правкой документации.
