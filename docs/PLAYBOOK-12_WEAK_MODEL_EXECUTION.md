# Echolet: Weak-Model Execution Playbook (PLAYBOOK-12)

> Порядок исполнения обновлён flow 001: сначала G0 из [DELIVERY-13](DELIVERY-13_SPRINT_PLAN.md) и проверка [RFC-18](RFC-18_CRYPTO_SELECTION.md). Номера задач сохранены для трассируемости, но выбор библиотеки J-001 выполняется на G0, а не после остальных пакетов. До закрытия G0 разрешены только изолированные feasibility harness/исправления безопасности и документов; основная реализация messaging ждёт доказательств. Текущая готовность — [STATUS_CURRENT](STATUS_CURRENT.md).

## 1. Назначение документа
Этот документ нужен для случая, когда проект реализует слабая или бесплатная модель, которая:

* плохо держит большой контекст;
* теряет архитектурную цель после 1-2 шагов;
* склонна смешивать UI, бизнес-логику, API и криптографию;
* часто забывает тесты, валидацию и ограничения безопасности.

Задача playbook — превратить реализацию Echolet в строго управляемый конвейер маленьких шагов.

---

## 2. Главный принцип
Слабая модель не должна "проектировать систему". Она должна **исполнять уже спроектированные атомарные задачи**.

Правильная роль слабой модели:

* создать один файл;
* реализовать одну функцию;
* написать один handler;
* покрыть один validator тестами;
* выполнить одну четкую миграцию структуры.

Неправильная роль слабой модели:

* придумывать протокол;
* менять security assumptions;
* переизобретать типы;
* объединять 5 подсистем в одном PR;
* заменять требования “как кажется логичнее”.

---

## 3. Canonical source order
При любой реализации модель обязана считать документы источниками истины в таком порядке:

1. `PROTOCOL-07_MVP_MESSAGE_FLOW.md`
2. `THREAT-08_MODEL.md`
3. `API-11_JSON_SCHEMAS.md`
4. `ARCH-09_REPOSITORY_STRUCTURE.md`
5. `TASKS-10_IMPLEMENTATION_BACKLOG.md`
6. `SEC-01_IDENTITY.md`
7. `REP-02_REPEATER_NODE.md`
8. `APP-03_MOBILE_CLIENT.md`
9. `PLAN-05_ROADMAP.md`

Если два документа кажутся противоречивыми, более прикладной и поздний по цепочке проектирования документ имеет приоритет только если он не ломает protocol/security baseline.

Практически это значит:

* protocol и threat model важнее красивого UI;
* JSON contracts важнее интуитивной формы API;
* repository structure важнее спонтанной организационной идеи модели.

---

## 4. Режим работы слабой модели

### 4.1. Одна задача за раз
Никогда не просить модель сделать больше одного atomic task из `TASKS-10_IMPLEMENTATION_BACKLOG.md` за один проход.

### 4.2. Один слой за раз
Нельзя в одной задаче смешивать:

* `packages/protocol`
* `packages/crypto-core`
* `packages/client-db`
* `packages/client-core`
* `apps/relay`
* `apps/mobile`

Исключение только одно: если задача — wiring уже существующих модулей с очень маленьким объемом кода.

### 4.3. Один критерий готовности
У каждой задачи должен быть один измеримый результат:

* файл создан;
* тест прошел;
* endpoint отвечает по схеме;
* validator отклоняет invalid payload.

## 5. Обязательный шаблон промпта для слабой модели
Каждую задачу нужно давать по одному и тому же шаблону.

```text
Контекст:
- Проект: Echolet MVP
- Следуй строго этим документам:
  1) PROTOCOL-07_MVP_MESSAGE_FLOW.md
  2) THREAT-08_MODEL.md
  3) API-11_JSON_SCHEMAS.md
  4) ARCH-09_REPOSITORY_STRUCTURE.md
  5) TASKS-10_IMPLEMENTATION_BACKLOG.md

Задача:
- Выполни только задачу <ID>
- Не меняй другие модули
- Не перепроектируй архитектуру

Что нужно сделать:
- <список шагов из backlog>

Ограничения:
- Не создавать новые типы, если они уже определены в protocol docs
- Не менять JSON contracts
- Не упрощать security checks
- Не добавлять лишние зависимости

Результат:
- Покажи какие файлы изменены
- Кратко опиши что реализовано
- Укажи как это проверено
```

Этот шаблон MUST использоваться без вольной переформулировки, иначе слабая модель начинает оптимизировать не туда.

## 6. Шаблон review-промпта для слабой модели
После каждой нетривиальной задачи нужно отдельно запускать проверочный проход.

```text
Проверь реализацию задачи <ID> в проекте Echolet MVP.

Проверь только:
1. Соответствие файлам и шагам задачи
2. Соответствие PROTOCOL-07_MVP_MESSAGE_FLOW.md
3. Соответствие THREAT-08_MODEL.md
4. Наличие минимальных тестов
5. Отсутствие лишних архитектурных отклонений

Не предлагай новый дизайн.
Верни только:
- найденные проблемы
- конкретные файлы
- минимальные исправления
```

---

## 7. Шаблон fix-промпта

```text
Исправь только перечисленные замечания для задачи <ID>.

Нельзя:
- рефакторить соседние модули
- менять публичные контракты
- добавлять новые фичи

Нужно:
- внести минимальные исправления
- сохранить совместимость с текущими docs
- кратко перечислить исправленные пункты
```

## 8. Строгие правила делегирования задач

### 8.1. Какие задачи безопасно давать слабой модели
Безопасно давать:

* создание TS types по готовой схеме;
* runtime validators;
* helper-функции для encoding;
* CRUD repository;
* простой HTTP handler по точному контракту;
* экран-заглушку;
* unit tests на already-defined logic.

### 8.2. Какие задачи опасно давать слабой модели без supervision
Опасно давать:

* выбор криптобиблиотеки;
* самостоятельное проектирование session bootstrap;
* threat-model решения;
* cross-module рефакторинг;
* multi-file migration со сменой контрактов;
* auth и signature verification flow без готового шаблона.

### 8.3. Какие задачи вообще нельзя давать слабой модели без предварительного шаблона
Нельзя без шаблона:

* mailbox challenge signature string;
* canonical JSON signing;
* prekey rotation logic;
* poisoned envelope handling;
* dedup semantics;
* TTL cleanup behavior.

## 9. Процесс выполнения одной задачи

### Шаг 1. Выбрать ровно одну задачу
Выбрать один `ID` из `TASKS-10_IMPLEMENTATION_BACKLOG.md`.

### Шаг 2. Подтянуть только нужный контекст
Передать модели только:

* задачу;
* связанные разделы из нужных документов;
* пути файлов.

Не загружать в нее весь проект, если это не нужно.

### Шаг 3. Попросить сделать только implementation
Не просить объяснять архитектуру. Архитектура уже зафиксирована.

### Шаг 4. Запустить отдельный review-pass
Даже если задача маленькая.

### Шаг 5. Если есть замечания — отдельный fix-pass
Не совмещать review и fix в одном промпте.

### Шаг 6. Только после этого переходить к следующей задаче

## 10. Stop conditions
Нужно останавливать слабую модель и не принимать результат, если она:

* меняет JSON contracts без запроса;
* переименовывает доменные сущности;
* упрощает security checks;
* добавляет "временные" заглушки без явной пометки;
* удаляет тесты;
* смешивает обязанности между слоями;
* пишет самодельную криптографию.

Если произошла одна из этих ситуаций, task считается не выполненным.

---

## 11. Разрешенные упрощения
Чтобы бесплатная модель реально справилась, разрешены только такие упрощения:

* один relay;
* одно устройство на пользователя на первом demo;
* только QR-contact exchange;
* только `delivered` receipts;
* только текстовые сообщения;
* только HTTP JSON API на MVP.

Запрещенные упрощения:

* убрать подписи;
* убрать challenge-response mailbox;
* убрать `PreKey Bundle`;
* хранить seed в обычной БД;
* принимать contact по callsign без fingerprint.

## 13. Handoff format между сессиями
Слабая модель плохо держит длинную историю, поэтому нужен обязательный handoff summary.

После каждой задачи нужно сохранять блок:

```text
Task completed: <ID>
Files changed:
- path/to/file1
- path/to/file2

What was implemented:
- ...

How it was verified:
- ...

Open issues:
- none / ...

Next recommended task:
- <ID>
```

Этот блок нужно хранить в отдельном журнале задач или в комментарии к PR.

---

## 14. Definition of done для слабой модели
Задача считается завершенной только если одновременно выполнены все пункты:

* изменены только ожидаемые файлы;
* контракт совпадает со спецификацией;
* есть минимум один тест или четкая ручная проверка;
* нет лишнего рефакторинга;
* нет security regression;
* есть handoff summary.

---

## 15. Антипаттерны, которые нужно пресекать

### 15.1. “Я заодно улучшил архитектуру”
Запрещено. Слабая модель почти всегда ломает совместимость.

### 15.2. “Я создал свой helper formatPayloadFlexible”
Запрещено, если это не следует из существующего контракта.

### 15.3. “Я сделал универсальный сервис на 500 строк”
Запрещено. Нужно дробить.

### 15.4. “Я не написал тест, потому что логика простая”
Для protocol/security кода это запрещено.

### 15.5. “Я изменил JSON, потому что так красивее”
Запрещено без обновления спецификации.

---

## 16. Роль сильной модели или человека-куратора
Даже если основную реализацию делает слабая модель, нужен куратор, который делает только 4 вещи:

* выбирает следующую атомарную задачу;
* выдает контекст в фиксированном шаблоне;
* запускает review-pass;
* не дает слабой модели выйти за границы спецификации.

Куратор не должен просить слабую модель "сделать умно". Он должен просить "сделать точно".

---

## 17. Итог
Если следовать этому playbook, даже слабая модель сможет двигать Echolet вперед без разрушения архитектуры.

Формула успеха:

* маленькие задачи;
* жесткие контракты;
* отдельный review-pass;
* нулевая свобода в protocol/security слоях.
