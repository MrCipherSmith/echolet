# Acceptance criteria

- AC1: Security and relay specifications consistently define HTTP JSON over TLS as the MVP transport and make no unsupported comparative metadata-privacy guarantee.
- AC2: Mailbox challenge/poll/ack documentation matches verified current client and Go handlers, including signing inputs and ownership checks.
- AC3: Roadmap and execution plan put crypto/mobile feasibility before dependent implementation, independent security review before sensitive-use pilot, and define explicit pilot go/no-go evidence.
- AC4: A single current readiness document separates target requirements, historical checks, current reproducible results and remaining blockers; other status documents link to it.
- AC5: Session feasibility has a code-grounded report and executable verification, with supported library path or concrete blocker; no simplified encryption is labelled production ratchet.
- AC6: Real-device messaging and background delivery, external security review, and actual user-pilot results are recorded before declaring product readiness; missing evidence keeps these tasks open.
